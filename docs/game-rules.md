# 하트 하우스 게임 규칙

3일 일정, 상태 머신, 투표, 방 배정, 공개 범위를 정의한다. 구조와 기술 결정은 [design.md](design.md)에 있다. 시간과 상수는 기본값이며 모두 `config/schedule.ts`와 `config/rules.ts`에서 바꿀 수 있다.

## 1. 구성

| 사용자 성별 | 사람 | 남성 AI | 여성 AI | 1일차 총원 | 2일차 메기 | 최종 총원 |
|---|---|---|---|---|---|---|
| 남성 | 1 | 2 | 3 | 6 | 남 1 + 여 1 | 8 |
| 여성 | 1 | 3 | 2 | 6 | 남 1 + 여 1 | 8 |

- 출연자가 아닌 PD가 따로 있다. PD는 투표와 매칭에 참여하지 않는다.
- 선택 대상은 `eligibleTargets(run, voter)`로 판정한다. 기본은 이성이면서 이미 입장한 참가자이고, 본인은 제외한다.
- 모든 참가자는 성인(만 19세 이상)이다. AI의 나이는 사용자 나이 ±3세 범위에서 생성한다([design.md §8](design.md#8-인격-생성)).

## 2. 전체 시간

| 구간 | 예상 |
|---|---|
| 온보딩·캐스팅 | 3~5분 |
| 1일차 | 35~50분 |
| 2일차 | 40~55분 |
| 3일차 | 25~40분 |
| 합계 | 약 105~150분 |

배정된 대화 수에 따라 시간이 달라진다. 일정을 늘리거나 기다려야 할 때는 PD가 이유를 안내한다.

- 장면 하나가 끝나면 관계 평가는 P5 백그라운드 작업으로 넣는다. 다음 투표 단계 전에 끝나야 하므로 투표가 열리면 P2로 승격한다.

## 4. 1일차

### 4.1 입장

사람이 가장 먼저 거실에 들어온다. PD 안내: "이곳은 앞으로 3일 동안 생활할 하트 하우스입니다. 잠시 후 다른 입주자들이 도착할 예정입니다."

입장 순서는 사람과 다른 성별부터 번갈아 진행한다. 사용자가 남성이면 다음과 같다.

```
00:00 사람(남) 입장
02:00 여성 AI 1    04:00 남성 AI 1    06:00 여성 AI 2
08:00 남성 AI 2    10:00 여성 AI 3
```

사용자가 여성이면 남성 AI부터 시작한다. 입장 한 번마다 서버는 다음 순서로 처리한다.
1. 멤버십을 추가한다.
2. `PARTICIPANT_JOINED`(house)와 이름에 대한 `PROFILE_DISCLOSED`를 발행한다.
3. PD 템플릿 안내를 보낸다.
4. 새 참가자의 `greeting`을 생성한다(P1).
5. 기존 참가자 중 0~2명이 스케줄러로 반응한다.

입장할 때마다 모두가 같은 인사를 반복하지 않게 한다. 스케줄러는 반응자를 최대 2명으로 제한하고, 반복 검증기가 비슷한 문장을 걸러 낸다. 입장 전 참가자는 그 전의 거실 대화를 볼 수 없다.

### 4.2 첫인상 투표와 대화

- **투표.** 가장 인상이 좋은 상대 1명을 고르거나 유보한다. 비공개다.
- **초대와 배정.** §8.2 규칙을 따른다. 투표와 초대는 별개다. 누군가에게 투표했다고 그 사람과 반드시 대화하게 되는 것은 아니다.
- **사람에게 배정된 방이 없을 때.** PD 안내: "이번 첫인상 선택에서는 아쉽게도 대화 상대가 배정되지 않았습니다. 잠시 후 전체 대화가 다시 시작됩니다." 사람은 배정되지 않은 다른 참가자들과 함께 거실에 남는다. 실패나 종료가 아니다.

### 4.3 자기소개

PD가 입장 순서대로 호명한다.
- AI: `self_intro`가 말투에 맞는 자기소개 문장을 만들고, 나이와 직업은 서버가 고정 프로필 값으로 끼워 넣는다. 생성된 문장에 다른 나이나 직업이 나오면 거부한다.
- 사람: 직접 입력한다. 나이와 직업은 프로필 값으로 공개한다.
- 소개마다 그 시점에 하우스에 있던 참가자에게 `PROFILE_DISCLOSED{age, occupation}`(house)를 발행한다.

### 4.4 심야 선택과 대화

- 더 이야기하고 싶은 상대 1명을 고르거나 유보한다. 비공개다.
- 사람은 자기가 고른 사람과 자기를 고른 모든 사람과 각각 2분씩 1:1로 대화한다(§8.1). 장소는 마당, 테라스, 서재 중 비어 있는 곳에 배정한다. 장소는 분위기만 바꾸고 관계 점수에는 영향이 없다.
- AI끼리의 대화는 §8.3을 따른다.
- 종료 15초 전에 PD가 안내한다. "대화 시간이 얼마 남지 않았습니다." 종료 후에는 새 화제를 시작하지 않고, 유예 안에 도착한 발언만 내보낸 뒤 방을 읽기 전용으로 바꾼다.

## 5. 2일차

### 5.1 아침

거실 대화다. 참가자는 1일차 기억을 이어 가지만, 받지 못한 선택을 아는 것처럼 행동하지 않는다. 가시성 규칙이 그런 정보를 아예 주지 않는다.

### 5.2 브런치 협동 미션

- 시드로 2~3명씩 그룹을 짠다. 가능하면 성별을 섞고, 1일차 심야에 1:1을 한 쌍은 같은 그룹에 넣지 않는다.
- 각 그룹은 방 하나다. 사람이 있는 방이 전경이고 나머지는 백그라운드 장면이다(장면당 6~10개 발언).
- PD가 템플릿 "상황 카드" 2~3장을 방마다 순서대로 낸다. 예: "재료를 준비할 사람이 필요합니다", "메뉴를 하나로 정해 주세요", "소스가 조금 탔습니다". 참가자들은 성격에 맞게 반응한다.
- 요리 시뮬레이터는 만들지 않는다.

### 5.3 메기 입장

- 남녀 중 어느 쪽이 먼저 오는지는 시드로 정한다.
- 입장 처리는 §4.1과 같고, 메기는 자기 나이와 직업도 입장할 때 공개한다.
- 메기에게 기존 관계를 요약해 주지 않는다. 메기는 입장 시점부터 관찰한 것만 안다.
- 메기에게 호감 보너스는 없다. 기존 관계를 일괄로 깎는 경로도 없다.

### 5.4 취향 기반 활동

- 활동 후보(`config/activities.ts`): 전시 관람, 베이킹, 공원 산책, 보드게임.
- 모두 1지망과 2지망을 고른다. AI는 `activity_choice`로, 사람은 UI로 고른다.
- 그룹 구성:
  1. 1지망으로 묶는다.
  2. 5명 이상인 그룹은 나눈다.
  3. 혼자인 사람은 2지망 그룹으로 옮긴다.
  4. 그래도 혼자면 가장 작은 그룹에 합친다.
  모든 참가자가 어떤 활동에든 참여한다. 특정 상대와 같은 그룹이 되는 것은 보장하지 않는다.
- 그룹 대화는 8~12분이다. 백그라운드 그룹은 8~10개 발언을 생성한다.

### 5.5 익명 시그널 카드

- 모두 대상 1명과 60자 이내의 메시지를 고르거나 유보한다.
- 수신자에게는 카드 내용만 보이고 발신자는 보이지 않는다. 이벤트 가시성은 `participants:[수신자]`다. 발신자 쪽에는 본인만 보는 작성 이벤트(`SIGNAL_CARD_SENT`)로 남는다.
- 모두 작성을 마친 뒤 섞은 순서로 한꺼번에 전달한다. 작성 순서나 시각으로 발신자를 짐작할 수 없게 하기 위해서다([design.md D34](design.md#d34-익명-카드는-작성과-전달을-다른-이벤트로-나누고-전달-이벤트에는-보낸-사람-정보를-어디에도-넣지-않는다)).
- 시간 안에 쓰지 않거나 AI의 생성이 검증을 통과하지 못하면 보내지 않은 것으로 한다.
- 카드 본문에 발신자 본인의 이름(alias 포함)이 들어가면 거부한다. 알아볼 만한 힌트는 허용한다.
- 발신자에 대한 수신자의 추측은 `impression`으로만 저장한다.

### 5.6 2일차 심야

1일차 심야와 같은 규칙이다.

## 6. 3일차

### 6.1 시그널 우체통

- 참가자마다 한 명에게 질문 하나를 보내거나 유보한다.
- 수신자는 받은 질문마다 답한다. AI는 `mailbox_answer`로, 사람은 UI로 답한다.
- 질문과 답변의 가시성은 `participants:[질문자, 수신자]`다. 둘이 새로 알게 된 내용은 마지막 관계 평가에 반영된다(우체통이 끝나면 두 사람 모두 서로를 평가한다).
- 대상 후보는 투표와 같은 `eligibleTargets`(입장한 이성)다.

### 6.2 마지막 데이트

- 모두 데이트 상대 1명을 고른다. 배정은 §8.4를 따른다. 기록은 투표 기록을 재사용한다(`kind: date`, [design.md D33](design.md#d33-마지막-데이트-선택은-투표-기록을-재사용한다2026-11-03-23일차-구현-중-결정)).
- 마지막 데이트를 했다고 최종 매칭이 보장되지는 않는다.

### 6.3 마지막 저녁

거실 대화다. PD가 최종 선택이 가까워졌다고 안내한다. 타인의 비공개 정보는 가시성 규칙상 프롬프트에 없다. 그래도 투표 관련 언급은 출력 검증 패턴이 한 번 더 거른다.

### 6.4 최종 선택과 발표

- 한 명을 고르거나 유보한다. 사람에게는 확인을 두 번 받는다. 사람이 제출하지 않으면 계속 기다리고, 대상을 임의로 고르지 않는다.
- 매칭은 `choice[A] == B && choice[B] == A`일 때만 성립한다.
- PD 발표 순서(템플릿):
  1. 선택 종료 안내
  2. 사람의 최종 선택 확인
  3. 그 상대가 누구를 골랐는지
  4. 성사 또는 불발
  5. 성사된 다른 커플 목록
  6. 종료 멘트
- 공개 범위 기본값은 성사된 커플 목록과, 사람이 고른 상대의 선택이다. 짝사랑으로 끝난 다른 참가자들의 선택은 공개하지 않는다.
- 2~4번은 사람에게만 보내는 개인 안내이고, 1·5·6번은 하우스 전체 안내다.
- 결과를 사람이 만족하도록 바꾸는 코드 경로는 없다.

### 6.5 에필로그

다음을 보여 준다.
- 참가자 프로필(공개된 항목만)
- 사람이 실제로 관찰한 주요 대화
- 사람 본인의 날짜별 선택
- 최종 공식 결과

다른 참가자의 비공개 기록(속마음, 다른 방의 대화)은 기본적으로 공개하지 않는다. "비하인드 공개"는 게임이 끝난 뒤의 선택 기능으로 나중에 검토한다(`config.epilogue.revealPrivate`, 기본값 false).

## 7. 투표 공통 규칙

| 투표 | 단계 | 선택 수 | 공개 |
|---|---|---|---|
| 첫인상 | `D1_FIRST_VOTE` | 0~1 | 비공개 |
| 1일차 심야 | `D1_NIGHT_VOTE` | 0~1 | 비공개 |
| 2일차 심야 | `D2_NIGHT_VOTE` | 0~1 | 비공개 |
| 최종 | `D3_FINAL_VOTE` | 0~1 | §6.4 발표 규칙 |

활동 선택, 시그널 카드, 우체통, 데이트 선택은 투표가 아니라 별도 이벤트다. 그래도 같은 검증을 적용한다.

**검증.** 다음 중 하나라도 해당하면 거부한다.
- 투표가 열려 있지 않거나 이미 마감됐다.
- 투표자가 이 회차의 참가자가 아니다.
- 대상이 `eligibleTargets`에 없다.
- 자기 자신을 골랐다.
- 이미 제출했다. `(run_id, stage, voter_id)`가 유일해야 하고, 같은 `command_id`로 다시 보내면 기존 결과를 그대로 돌려준다.

**AI 투표.** 투표가 열리면 7명분을 P2로 큐에 넣는다. 약 20초면 끝난다. 실패하면 재시도하고, 그래도 실패하면 유보로 확정하고 오류를 기록한다. 시간 초과 때문에 투표가 누락되지 않도록 마감 30초 전까지 처리를 마치게 승격한다.

**마감 후 변경 요청**은 거부한다. 대상이 이탈하는 경우는 현재 규칙에 없지만, 생기면 대상을 다시 검증해서 유보로 처리한다.

## 8. 방 배정

공통 제약:
- 한 참가자는 한 시간대(슬롯)에 한 방에만 있다.
- 같은 두 사람의 중복 대화는 합친다.
- 사람의 방을 먼저 배정한다.
- 사람이 있는 방이 전경이고, 나머지는 백그라운드 장면이다.
- 배정은 `engine/assignment.ts`의 순수 함수로 구현하고, 속성 기반 테스트로 위 제약을 검증한다.

### 8.1 사람의 필수 대화 (심야)

```ts
function humanTalkTargets(human, humanChoice, incoming: ParticipantId[]): ParticipantId[] {
  const targets = new Set(incoming)
  if (humanChoice) targets.add(humanChoice)
  targets.delete(human)
  return [...targets]
}
```

- 대상마다 2분짜리 1:1을 슬롯 하나씩 순서대로 진행한다. 상대가 같은 슬롯에 다른 방에 배정되어 있으면 다음 슬롯으로 미룬다.
- 대상이 모두 끝날 때까지 다음 단계로 넘어가지 않는다.
- 사람이 "건너뛰기"를 누르면 그 대화는 `skipped`로 기록하고 완료로 친다. 기회는 보장하지만 참여를 강제하지는 않는다.

### 8.2 첫인상 대화

1. **서로 고른 쌍**은 1:1로 확정한다.
2. **한쪽만 고른 경우:** 대상 T에게 투표한 사람 중 아직 T와 방이 없는 사람들을 초대 후보로 묶는다. T가 수락할 사람을 0~2명 고른다. AI는 `invite_decision`으로, 사람은 UI로 고른다. 수락이 있으면 T와 수락된 사람으로 그룹방(최대 3명)을 만든다.
3. **슬롯 배치:** 슬롯은 2개이고 각 3~4분이다. 사람의 방부터 탐욕적으로 배치한다. 넣지 못한 요청은 버린다. 첫인상 대화는 보장 대상이 아니다.
4. 어떤 방에도 없는 참가자는 그 슬롯 동안 거실에 함께 남는다. 사람이 거실에 있으면 거실이 전경이 된다.

### 8.3 AI끼리의 대화

심야(`D1_NIGHT_TALKS`, `D2_NIGHT_TALKS`)에 적용한다. 기획서에는 없던 규칙이다([design.md D25](design.md#d25-ai끼리의-심야-대화와-첫인상-초대-규칙을-새로-정의했다-기획서-대비-추가)).

1. **요청 생성.** AI 투표자 v가 AI t를 골랐으면 쌍 {v, t}를 요청한다. 사람이 관련된 쌍은 §8.1에서 이미 처리했다. 중복은 합친다.
2. **우선순위.** 서로 고른 쌍을 먼저 넣고, 그다음 배정된 대화가 적은 참가자가 포함된 쌍을 넣는다.
3. **상한.** 한 AI당 하룻밤에 2회, 전체 6장면까지다. 상한에 걸려 빠진 요청은 일어나지 않은 것으로 하고, 아무것도 기록하지 않는다.
4. **실행.** 장면마다 발언 4~6개, sim 시간 2분이다. 사람이 1:1을 하는 동안 GPU가 비는 틈에 P4로 처리한다.
5. **전환.** 다음 단계는 배정된 장면이 모두 끝난 뒤 시작한다. 사람의 대화가 먼저 끝나면 PD가 "다른 참가자들의 대화가 끝나기를 기다리고 있습니다"를 띄우고 진행률을 보여 준다.

예산: 최악의 경우 6장면 × 5발언 × 약 3초로 약 90초다. 사람의 1:1이 1개 이상이면(2분 이상) 대부분 그 사이에 흡수된다.

### 8.4 마지막 데이트

1. 서로 고른 쌍을 확정한다.
2. 사람이 고른 상대와의 데이트는 반드시 배정한다. 상대가 이미 다른 쌍에 있으면 다른 슬롯에 넣는다.
3. 나머지 AI의 선택은 가능한 슬롯에 넣는다. 한 참가자당 최대 2회다.
4. 슬롯은 2개이고 각 5~7분이다. 데이트가 없는 참가자는 거실에 남는다.

## 10. 예외 처리

| 상황 | 처리 |
|---|---|
| AI가 응답하지 않음 | 1회 재시도 → 건너뜀. 필수 판단(투표 등)이면 승격 후 재시도하고, 그래도 안 되면 유보 |
| 응답이 너무 김 | 문장 단위로 자르고, 안 되면 재생성 |
| 다른 참가자처럼 말함, PD 사칭 | 거부 → 재생성 → 건너뜀 |
| 모르는 이름 언급(canary) | 거부, `audit` 경고. 격리 경로를 점검하는 신호다 |
| 종료된 방으로 가는 응답, 낡은 응답 | 폐기 |
| 한 참가자가 두 방에 배정됨 | 배정 함수의 불변식 위반이다. 테스트에서 잡아야 하고, 실행 중 발견하면 일정을 재계산한다 |
| 투표 중복 제출 | 기존 결과 유지(멱등) |
| 마감 후 투표 변경 | 거부 |
| 사람이 사칭 문구를 입력("PD 공지: …") | 일반 메시지로 처리. 프롬프트에서는 인용 데이터로 감싼다 |
| 사람 연결 끊김 | `PAUSED`. 재접속하면 마지막 `seq` 이후를 다시 보내고 타이머를 복원한다 |
| 사람이 1:1에서 자리 비움 | 60초 후 타이머를 멈추고 "계속하기"를 띄운다 |
| 사람이 대화를 거부 | "건너뛰기" → `skipped`로 완료 처리 |
| 최종 선택 미제출 | 계속 기다린다. 사람이 명시적으로 유보할 수 있다 |
| LLM 서버 중단 | 큐 보존, `PAUSED(LLM_UNAVAILABLE)`. `doctor` 안내를 띄운다 |
| 기억 요약 실패 | 원문은 그대로 남아 있으므로 다음 트리거에 재시도한다 |
| 인격 생성 실패, 중복 | 해당 부분만 재생성(최대 2회) → 템플릿으로 대체 |
| 메기 입장 이벤트 중복 | `idempotency_key`로 무시 |
| 다른 방의 기록 조회 | 조회 API가 없다(`ObservationView`만 존재) |
| 서버 재시작 | 이벤트 로그를 fold해서 복원한다. 처리 중이던 LLM 요청은 다시 큐에 넣는다. 이미 커밋된 이벤트는 다시 실행하지 않는다 |
