# 하트 하우스 (love-with-ai) 설계

이 문서가 설계의 정본이다. 구현 진행 상황과 다음 할 일은 [status.md](status.md)에 있다. 원본 기획서 v2.0(2026-11-02)을 바탕으로 검토 피드백과 사용자 결정을 반영했다. 3일 일정, 투표, 방 배정 같은 게임 규칙은 [game-rules.md](game-rules.md)에 있다. 원본 기획서와 이 문서가 다르면 이 문서를 따른다. 원본과 달라진 점은 §3 결정 기록에서 "기획서 대비"로 표시했다.

## 1. 확정 사항

| 항목 | 결정 |
|---|---|
| 제품 | 사람 1 + AI 7(2일차 메기 2명 포함) + PD. 3일짜리 연애 리얼리티를 실시간 채팅으로 진행한다. 한 판은 약 2시간이다 |
| 대상 | 성인 전용(만 19세 이상) |
| 모델 | Qwen3.5-4B GGUF Q4_K_M, thinking off |
| 프로필 사진 | FLUX.2 [klein] 4B, stable-diffusion.cpp(WSL CUDA). 캐스팅 때 LLM과 GPU를 교대로 쓴다(D22, D27) |
| 추론 | llama.cpp `llama-server`. WSL2 안에서 CUDA로 빌드하고 `127.0.0.1`에만 바인딩한다. 슬롯은 1개(`-np 1`) |
| 최소 사양 | RTX 3060 Ti (VRAM 8GB) |
| 컨텍스트(KV) | `-c 102400`(약 100K). 항상 명시한다(D26) |
| 백엔드 | Node 22 LTS 이상 + TypeScript 6 (개발은 Node 24 LTS) |
| 프론트엔드 | React + TypeScript + Vite |
| 저장소 | SQLite(WAL) |
| 네트워크 | 실행과 테스트 트래픽은 모두 로컬에 머문다. 외부 통신은 모델·패키지를 다운로드할 때뿐이다 |

## 2. 핵심 원칙

1. **진행자는 코드다.** 시간, 일정, 방, 권한, 투표, 매칭, 상태 전이는 서버가 결정한다. LLM은 대사와 판단만 만든다. LLM이 대사로 무엇을 묘사하든, 서버 이벤트가 없으면 일어나지 않은 일이다.
2. **독립성은 데이터 접근 제어로 보장한다.** 참가자 8명과 PD는 모델 하나를 공유한다. 독립성은 LLM 세션을 나눠서 얻는 것이 아니다. 각 호출에 무엇을 넣을지를 가시성 규칙이 결정하는 데서 나온다.
3. **사실은 이벤트에서만 나온다.** 확인된 사실은 서버의 구조화 이벤트로만 생긴다. LLM이 만든 요약과 평가는 전부 인상(impression)으로 취급한다.
4. **공정성은 구조로 보장한다.** 사용자에게 특혜를 주지 않는다는 원칙과 AI의 독립적인 취향은 "사용자를 우대하지 마라" 같은 프롬프트 지시에 기대지 않는다. 숨은 취향 벡터, 사용자 표지 제거, 후보 순서 섞기로 구조적으로 보장한다.
5. **격리는 강제하고 검증한다.** 모든 LLM 호출에 무엇이 들어갔는지 `deliveries`에 기록한다. 사후 `audit`이 가시성 규칙과 기계적으로 대조한다.
6. **회차는 독립이다.** 모든 데이터는 `run_id`로 범위를 제한한다. 이전 회차를 참조하는 경로는 두지 않는다.
7. **틀릴 바에는 말하지 않는다.** 검증에 실패한 출력은 한 번 재생성하고, 그래도 실패하면 건너뛴다. 서버가 내용을 지어내서 내보내지 않는다.

## 3. 결정 기록

각 항목은 결정, 이유, 기각한 대안 순서로 적는다.

### D1. 백엔드는 Node 22 LTS + TypeScript, pnpm workspace 모노레포
- 이유: 프론트와 백엔드가 `shared` 패키지로 타입을 공유한다. zod 스키마 하나에서 WebSocket 프로토콜 타입, llama.cpp에 넘길 JSON Schema(zod 4의 `z.toJSONSchema`), 런타임 검증을 모두 얻는다.
- 기각: Python(FastAPI). mafia-with-ai 코드를 재사용할 수 있지만 프론트와 타입을 공유할 수 없다. 패턴(이벤트 소싱, deliveries, audit)은 언어와 무관하게 옮길 수 있다.
- 요구 사항: Node 22 LTS 이상(최신 Vite는 20.19 이상을 요구한다). pnpm은 corepack으로 켠다.

### D2. 성인 전용(만 19세 이상). 기획서 대비 변경
- 이유: 미성년자용 별도 연령 그룹은 위험에 비해 얻는 것이 적다. 온보딩에서 만 19세 미만이면 진행하지 않는다.
- 기각: 미성년자 그룹을 따로 두고 같은 그룹끼리만 매칭하는 방식(기획서 원안).

### D3. llama.cpp는 WSL2 안의 CUDA 빌드로 실행한다
- 이유: 게임 서버와 같은 OS에서 `127.0.0.1`로 통신하고, 빌드·실행·벤치마크 스크립트를 하나로 관리한다.
- 기각: Windows 네이티브 `llama-server.exe`(기획서 예시). WSL↔Windows 네트워킹과 두 OS의 도구 체인을 따로 관리해야 한다.

### D4. 모델은 Qwen3.5-4B Q4_K_M으로 고정한다
- 이유: 사용자 결정. 8GB에 여유가 있고 지연이 짧다.
- 구조: 모델은 `LlmPort` 뒤에 숨긴다. 모델을 바꿔도 Gateway 설정만 달라진다.
- 재검토 조건: Phase 2 품질 평가(§15.4)에서 참가자 간 말투 구별이 기준에 못 미치면 모델 결정을 사용자와 다시 논의한다. 임의로 바꾸지 않는다.

### D5. thinking off는 요청마다 `chat_template_kwargs: {"enable_thinking": false}`로 명시한다
- 이유: Qwen3.5 소형 모델은 기본값이 off라고 알려져 있다. 그래도 템플릿이 바뀌어도 안전하도록 요청에 명시한다. 요청 단위로 제어하면 나중에 "투표만 thinking on" 실험을 서버 재시작 없이 할 수 있다.
- 기각: 서버 플래그(`--reasoning off`)에만 의존하는 방식. 플래그 이름은 빌드마다 다를 수 있으니 Phase 1에서 `llama-server --help`로 확인한다.

### D6. 이벤트 로그가 진실의 원천이다
- 이유: 재개, 감사, 재현, 기억의 근거 추적이 모두 이벤트 로그 하나로 해결된다. `messages`, `votes`, `relationships` 같은 테이블은 이벤트를 접어서(fold) 만든 projection이다.
- LLM 출력도 이벤트(`LLM_OUTPUT_ACCEPTED`)로 저장한다. 그래서 재생(replay)할 때 모델을 다시 부르지 않고 같은 결과를 얻는다.
- 기각: `messages`와 `events`에 본문을 이중으로 저장하는 방식(기획서 §43). 둘이 어긋날 수 있다.

### D7. 사실은 구조화 이벤트에서만 나오고, LLM이 만든 기억은 인상이다. 기획서 대비 변경
- 이유: 기획서 §8.4의 "실제 대화에 없었다면 사실로 저장하지 않는다"를 자동 검증하려면 의미를 이해해야 하고, 4B 모델로는 믿을 수 없다.
- 방법: 나이·직업 공개(`PROFILE_DISCLOSED`), 입장, 투표 결과 발표처럼 서버가 아는 사실만 `known_facts`가 된다. 요약과 관계 평가는 `impression`으로 저장한다.
- 한계: 자유 대화 속 사실("저 부산 살아요")은 MVP에서 사실로 추출하지 않는다. 원문 대화와 요약 속에 인상으로만 남는다.

### D8. 출력 검증은 규칙 기반으로만 한다. 기획서 대비 범위 축소
- 이유: "명백한 모순", "존재하지 않는 사건", "미래 사건 언급"을 판정하려면 판정용 LLM을 한 번 더 불러야 한다. 호출이 두 배가 되고, 판정자도 같은 4B라 정확도를 기대하기 어렵다.
- 범위: 스키마, 길이, 다른 사람 대사 대리 작성, PD·시스템 사칭, 모르는 이름 언급(canary), 종료된 방이나 낡은 컨텍스트, 직전 발언 반복(§7.5).
- 기각: LLM 판정자. 나중에 비동기 품질 측정용으로만 고려한다. 실시간 경로에는 넣지 않는다.

### D9. 숨은 취향 벡터와 결정론적 궁합을 LLM 판단과 섞는다. 기획서 대비 추가
- 이유: 소형 instruction 모델은 모두를 좋게 평가하는 경향이 있다. 그대로 두면 투표가 한쪽에 몰리거나 무작위처럼 나온다.
- 방법: 캐스팅할 때 참가자마다 숨은 취향과 싫어하는 성향을 시드로 만들고, 서버가 궁합을 계산한다. 궁합은 숫자로 프롬프트에 넣지 않는다. 노출량에 비례해 "결이 맞는다 / 어딘가 다르다" 같은 자연어 힌트로 바꿔 넣는다(§10.2).

### D10. 관계 변화는 범주형 변화량으로 받는다
- 방법: LLM은 축마다 `-2..+2`와 근거를 출력하고, 서버가 단위 환산과 상하한을 적용한다. 변경할 때마다 `RELATIONSHIP_UPDATED` 이벤트로 이력을 남긴다.
- 기획서 대비: 기획서 §43.5의 `relationships` 테이블에는 이력이 없어서 §9.3 "변화 이력을 남긴다"와 모순이었다. 이벤트 로그로 해결한다.
- 기각: LLM이 0~100 점수를 직접 쓰는 방식. 노이즈가 크다.

### D11. 인격 생성은 "시드 풀 + 분할된 LLM 생성 + 예시 대사"로 한다
- 방법: 이름, 직업, 지역, 취미는 `config/pools/`에서 시드로 뽑는다. LLM은 배경, 가치관, 말투 묘사, 예시 대사만 작은 JSON 여러 번으로 나눠 만든다.
- 이유: 4B 모델은 이름과 직업을 반복해서 만든다. 1,000토큰짜리 한 덩어리로 생성하면 일부만 다시 만들 수 없다.
- 메기를 포함한 7명을 온보딩 때 한 번에 생성한다. 기획서 §3.2의 "5명"과 §4.5의 "메기 사전 생성"이 서로 맞지 않던 부분을 통일했다.

### D12. 숫자 성향은 스케줄러용이고, 프롬프트에는 자연어와 예시 대사를 넣는다
- 이유: `extraversion: 35` 같은 숫자를 4B 모델은 거의 반영하지 못한다. 말투 차이를 내는 데 가장 효과가 큰 것은 참가자마다 고정한 예시 대사 3~5줄(few-shot)이다.
- 추가로 참가자마다 temperature를 기본값 ±0.1 안에서 다르게 준다.

### D13. 존댓말·반말은 참가자 쌍마다 상태로 관리한다
- 이유: 상태로 두지 않으면 모델이 말할 때마다 높임 수준이 흔들린다.
- 방법: 기본은 존댓말이다. 관계 평가에서 "말을 놓기로 했다"는 근거와 함께 전환이 제안되면 `SPEECH_LEVEL_CHANGED` 이벤트로 바꾼다. 다시 존댓말로 되돌리는 것은 자동으로 하지 않는다.

### D14. GPU 요청은 단일 우선순위 큐에서 직렬로 처리한다
- 방법: 슬롯 1개, 워커 1개. 우선순위는 P0~P5(§7.6)이고, 마감이 다가오면 승격한다. 한 참가자에게 동시에 진행 중인 요청은 하나뿐이다.
- 기각: `-np 2` 이상. 측정 전에는 복잡도만 늘어난다. Phase 6에서 실측 후 재검토한다.

### D15. 시간은 단조 시계로 재고, Clock·Rng·IdGen을 주입한다
- 이유: 이 WSL은 벽시계가 30초마다 약 2.3초씩 뒤로 간다. 타이머를 `Date.now()`로 재면 튄다.
- 방법: 경과 시간은 `performance.now()` 기반 `Clock`으로 잰다. 엔진은 `Clock`, `Rng`, `IdGen`을 주입받는다. 저장할 때는 절대 시각이 아니라 남은 시간(`remaining_ms`)을 저장한다.

### D16. 모든 LLM 호출의 입력을 `deliveries`에 기록하고 `audit`으로 검증한다
- 이유: 정보 격리(원칙 B)를 증명하는 가장 확실한 방법이다. mafia-with-ai에서 검증한 패턴이다.
- canary: 입장 전 메기의 이름, 비공개 투표 대상처럼 특정 시점에 특정 참가자가 알 수 없는 값을 감시한다. 그런 값이 컨텍스트나 출력에 나타나면 위반이다.

### D17. FakeLlm과 헤드리스 시뮬레이션을 먼저 만든다
- 이유: GPU 없이 3일 전체를 수천 번 자동으로 돌려 상태 머신, 방 배정, 격리를 검증할 수 있다. 프론트엔드 개발도 FakeLlm 위에서 진행한다.

### D18. PD 멘트는 MVP에서 전부 템플릿으로 한다
- 이유: GPU 호출을 아낀다. 공식 안내는 틀리면 안 되는 정보다.
- LLM으로 PD 멘트에 변주를 주는 것은 P3 우선순위의 선택 기능으로 나중에 붙인다.

### D19. 프롬프트에서 사용자를 표시하지 않는다
- 이유: 원칙 D(사용자 특혜 금지)를 구조로 보장한다. AI 컨텍스트에서 사용자는 다른 참가자와 똑같이 이름으로만 나타나고, "사용자", "플레이어" 같은 표지가 없다.
- 사용자가 입력한 성격 설명은 AI에게 주지 않는다. 사용자가 대화에서 직접 말한 것만 AI가 안다.

### D20. 투표 출력은 후보 ID `enum`으로 제한하고, 후보 순서는 매번 섞는다
- 이유: 존재하지 않는 대상을 고르는 형식 오류와, 목록 앞쪽을 고르는 위치 편향을 막는다.

### D21. 관계 증거량을 정규화한다. 기획서 대비 추가
- 이유: 사용자와의 1:1은 2분을 꽉 채우지만, AI끼리의 백그라운드 장면은 발언 4~6개로 압축된다. 그대로 두면 AI끼리의 관계는 늘 근거가 부족하고, 의도와 달리 사용자 쪽으로 관계가 기운다.
- 방법: 노출량을 포화 함수로 계산하고, 백그라운드 장면의 발언에는 가중치를 더 준다(§10.2).

### D22. 프로필 사진은 FLUX.2 [klein] 4B + stable-diffusion.cpp로 캐스팅 때 생성한다. 기획서 대비 P2에서 본 범위로 올림
- 결정: 사용자 결정(2026-11-02). 처음에는 "P2로 미루고 기본 아바타"였는데 개정했다. 구현 방법은 §8.3에 있다.
- 모델은 FLUX.2 [klein] 4B다. Apache 2.0 라이선스이고, 4스텝으로 증류된 모델이며, 텍스트 인코더는 Qwen3-4B다. 2026-01에 나와서 도구 지원이 성숙했다.
  - 기각: FLUX.3 Image Klein(2026-10-15, 5.6B). 품질 기대치는 더 높지만 나온 지 2주라 도구 지원이 초기 단계이고, 라이선스가 FLUX Kommunity다. `ImagePort` 뒤에서 교체 후보로 둔다.
- 엔진은 stable-diffusion.cpp다. llama.cpp와 같은 계열이고, WSL CUDA 단일 바이너리에 GGUF를 쓰며 Python이 필요 없다.
  - 기각: ComfyUI. Python과 PyTorch 스택이 추가되고 무겁다.
- 시점은 캐스팅 중 GPU 교대다. 8GB에는 LLM(약 7GB)과 이미지 모델이 동시에 올라가지 않으므로 `GpuLease`로 상호 배제한다(D27).
  - 기각: 미리 만들어 둔 사진 풀. 캐스팅은 즉시 끝나지만 회차 사이에 사진이 반복되어 회차 독립(원칙 6)이 약해진다.
- 실패하면 기본 아바타를 쓴다. 사진 생성이 실패해도 게임 시작은 막지 않는다.

### D26. 컨텍스트는 약 100K로 항상 명시한다. 기획서 대비 변경
- 결정: 사용자 결정. 최소 사양(RTX 3060 Ti, 8GB) 기준 `-c 102400`이다. 값은 `config/llm.ts`에 둔다.
- `-c`를 생략하지 않는다. 생략하면 llama.cpp는 모델의 학습 컨텍스트를 쓰는데, Qwen3.5는 기본 컨텍스트가 262,144로 알려져 있어 8GB에 들어가지 않는다. 정확한 값은 Phase 1에서 GGUF 메타데이터로 확인한다.
- VRAM 추정: full attention 층만 KV를 쓴다. 커뮤니티 모델 카드 기준(full attention 8층, KV 헤드 4개, 헤드 차원 256, f16)이면 토큰당 약 32KB다. 그러면 100K ≈ 3.2GB다. 여기에 가중치 약 2.8GB와 계산 버퍼를 더해도 100K 설정이 8GB 안에 들어간다. 층 구성 수치는 출처마다 달라서 Phase 1에서 실측한다. 넘치면 KV를 `q8_0`으로 양자화하는 것을 먼저 검토한다.
- 호출 하나에 넣는 프롬프트 예산은 그대로 약 3k다(§9.3). 소형 모델은 컨텍스트가 길수록 품질이 떨어지고 프롬프트 처리 시간도 늘어난다. 큰 `-c`는 여유분이다. llama.cpp는 전체 `-c`를 슬롯 수로 나누므로, 나중에 `-np`를 늘리는 실험(Phase 6)도 이 여유분 안에서 할 수 있다.
- 기각: 기획서의 `-c 8192`. 정상 경로에서는 충분하지만, 슬롯을 늘리거나 예산을 조정할 여지가 없다.

### D27. 게임 서버가 추론 프로세스를 소유하고, GPU를 임대(lease) 방식으로 나눈다
- 이유: LLM과 이미지 모델을 바꿔 올리려면 누군가 프로세스를 띄우고 내려야 한다. 사람이 손으로 하면 교대가 불가능하다.
- 방법: `InferenceSupervisor`가 `llama-server`와 stable-diffusion.cpp 프로세스를 띄우고, 헬스 체크를 하고, 종료한다. `GpuLease.acquire('llm' | 'image')`는 한 번에 한 쪽만 GPU를 쓰게 한다. 상대 쪽 프로세스를 내리고 VRAM이 비워진 것을 확인한 뒤 넘겨준다.
- 바이너리와 모델 경로는 `config/inference.ts`(환경 변수로 덮어쓸 수 있음)에 둔다. `doctor`가 경로, 버전, CUDA를 진단한다.
- 포트에 이미 떠 있는 llama-server가 이전에 이 앱이 띄운 것(PID 파일)이면 이어받고, 모르는 서버면 시작을 거부한다. 내리지 못하는 서버를 쓰면 GPU 교대가 조용히 실패하기 때문이다.

### D23. 프론트엔드는 사람에게 보이는 정보만 받는다
- 이유: 브라우저 개발자 도구로 비공개 정보를 볼 수 없어야 한다. 서버는 AI에게 적용하는 가시성 함수로 사람의 시점을 만들어 보낸다.
- 관전(god) 뷰는 개발 플래그(`--dev-observer`)로만 켜는 별도 엔드포인트다.

### D24. 저장소는 SQLite + better-sqlite3
- 이유: 단일 프로세스, 로컬, 트랜잭션이 필요하다. 동기 API라 이벤트를 추가하고 projection을 갱신하는 일을 한 트랜잭션으로 묶기 쉽다.
- 기각: `node:sqlite`(Node 22에서 아직 실험 단계), PostgreSQL(로컬 단일 사용자에게는 과하다).

### D25. AI끼리의 심야 대화와 첫인상 초대 규칙을 새로 정의했다. 기획서 대비 추가
- 이유: 기획서에는 사용자의 필수 대화만 규칙이 있었다. AI끼리 몇 쌍이 언제 대화하는지 정하지 않으면 GPU 예산을 잡을 수 없다.
- 규칙은 [game-rules.md §8](game-rules.md#8-방-배정)에 있다.

### D28. TypeScript는 6으로 고정한다(2026-11-02, 구현 중 결정)
- 이유: 설치 시점의 최신인 TypeScript 7(네이티브 Go 포트)을 typescript-eslint가 아직 지원하지 않는다. 린트를 품질 게이트에서 뺄 수 없으므로 생태계가 지원하는 6을 쓴다.
- 재검토 조건: typescript-eslint가 7을 지원하면 올린다. 코드는 7에서도 타입 검사를 통과하는 것을 확인했다.

### D29. projection은 메모리에서 fold로 만들고, SQLite에는 원천만 저장한다
- 방법: 회차 하나가 SQLite 파일 하나다(`runs/<run_id>/run.sqlite`). 저장하는 테이블은 `events`(원천), `deliveries`(감사), `llm_calls`(운영), `meta`, `schema_version`이다. 참가자, 방, 투표, 관계, 기억은 `RunState`가 이벤트를 접어서 만든다(`engine/state.ts`).
- 이유: 한 판의 이벤트는 수백~수천 개라 메모리 fold가 충분히 빠르다. 테이블을 이중으로 두면 둘이 어긋날 수 있다(D6).
- 기각: 기획서 §43의 projection 테이블 전부를 SQL로 유지하는 방식. 나중에 회차 간 통계나 외부 조회가 필요해지면 그때 파생 테이블을 만든다.

### D30. 새 입주자는 이미 와 있는 사람들의 이름을 입장 순간에 안다(감사로 발견)
- 문제: 처음에는 이름 공개 이벤트가 하우스 가시성뿐이었다. 그래서 늦게 들어온 참가자는 먼저 와 있던 사람들의 이름 공개를 관찰하지 못했고, 투표 기억을 만들 때 서버가 아는 실명이 새어 나갔다. 시뮬레이션 audit의 `canary_in_prompt`가 잡아냈다.
- 결정: 입장할 때 기존 입주자들의 이름을 새 입주자에게만(`participants` 가시성) 공개한다. 실제로 마주 보고 인사하는 순간이라 현실과도 맞다. 선택 기억은 항상 그 참가자 시점에서 아는 이름으로 쓴다.

### D31. 어떤 참가자의 전체 이름도 다른 참가자의 부르는 이름을 품으면 안 된다(감사로 발견)
- 문제: 성과 이름을 붙이면 "정우진"이 "최정우"의 "정우"를 품는다. 이러면 호칭 지목("정우씨")과 canary 검사가 모호해진다. 시드 1,000개 시뮬레이션에서 6건이 나왔다.
- 결정: 캐스팅에서 이런 조합을 거부한다(사용자 이름 포함). 부르는 이름은 `engine/aliases.ts`의 `givenName` 하나로만 계산한다. 한글 3글자면 성 1글자, 4글자면 성 2글자를 떼고, 영문 닉네임이나 2글자 이름은 그대로 쓴다.

### D32. 플레이 모드는 하나다: 항상 실제 모델(GPU)로 돈다(2026-11-03, 사용자 결정)
- 결정: `npm run dev`·`npm run start`로 띄우는 플레이 서버는 항상 llama.cpp와 stable-diffusion.cpp로 돈다. 필요한 실행 파일·모델이 없으면 빠진 파일과 설치 명령을 알려 주고 시작하지 않는다.
- 이유: 개발 편의용 가짜 모드가 기본값이던 탓에, 사용자가 가짜 AI 응답을 실제 게임으로 착각했다.
- FakeLlm·FakeImage는 자동 테스트와 헤드리스 시뮬레이션(`npm run sim`) 안에서만 조립한다. 사용자 경로에는 없다.
- 기각: 설치 여부에 따른 자동 전환, 테스트 모드 표시 배지. 모드가 둘인 것 자체가 혼란의 원인이다.

### D33. 마지막 데이트 선택은 투표 기록을 재사용한다(2026-11-03, 2·3일차 구현 중 결정)
- 결정: `VoteKind`에 `date`를 더하고, `VOTE_OPENED`·`VOTE_COMMITTED`·`VOTE_CLOSED`와 `runVote`를 그대로 쓴다.
- 이유: game-rules.md §7은 데이트 선택을 "투표가 아니지만 같은 검증을 적용"하는 별도 이벤트로 둔다. 필요한 것(본인만 보는 가시성, 대상 검증, 멱등, 마감, AI 실패 시 유보)이 투표와 똑같다. 별도 이벤트를 만들면 같은 코드를 한 벌 더 갖게 된다.
- 결과에는 영향이 없다: 매칭은 `final` 투표만으로 계산한다. 에필로그의 "나의 선택"에는 데이트 선택도 함께 나온다.
- 활동 지망(1지망·2지망 두 값)과 카드·우체통(본문이 있음)은 모양이 달라 각자의 이벤트를 둔다.

### D34. 익명 카드는 "작성"과 "전달"을 다른 이벤트로 나누고, 전달 이벤트에는 보낸 사람 정보를 어디에도 넣지 않는다
- `SIGNAL_CARD_SENT{senderId, targetId, text}`는 보낸 사람만 본다. `SIGNAL_CARD_RECEIVED{recipientId, text}`는 받는 사람만 보고, actor는 `server`다. 카드 id도 두지 않는다. id 순서가 보낸 사람을 암시할 수 있기 때문이다.
- 전달은 모두가 작성을 마친 뒤 한꺼번에, 시드로 섞은 순서로 한다. 작성 완료 순서나 시각으로 보낸 사람을 짐작할 수 없게 하기 위해서다.
- 카드 본문에 보낸 사람의 이름(호칭 변형 포함)이 있으면 AI는 출력 검증에서, 사람은 명령 검증에서 거부한다. audit은 `card_sender_leak`(본문 속 보낸 사람 이름)과 `private_visibility`(카드·활동 지망·우체통이 당사자 밖으로 보임)를 확인한다.
- AI는 받은 카드와 우체통 문답을 `ObservationView.privateSignals()`로만 읽는다. 투표·카드·우체통 작업의 "[나만 아는 일]" 칸과, 관계 평가·하루 요약의 관찰 기록에 들어간다.

### D35. 브런치·활동의 상황 카드는 PD 안내로 방에 내고, 대화 맥락에 PD 안내를 함께 넣는다
- 상황 카드(game-rules.md §5.2, 활동별 카드)는 `PD_ANNOUNCED{key: 'situation_card'}`로 그 방에 낸다. `ObservationView.roomMessages()`가 그 방의 PD 안내도 "PD 안내" 화자로 끼워 넣으므로, 참가자들은 카드에 반응해서 말한다. 사람이 보는 방의 장면은 카드가 나오면 한 명이 먼저 반응하게 한다.
- 첫 카드는 방이 열릴 때 내고, 첫 발언은 그 카드에 대한 반응(`reply`)으로 시작한다. 사람이 있는 방에는 남은 카드를 대화 시간 동안 고르게 나눠 낸다. 백그라운드 방은 첫 카드만 받는다. 발언 수가 정해진 짧은 장면이라, 시간에 맞춰 카드를 내면 장면이 이미 끝난 뒤일 수 있기 때문이다.
- 카드 문구는 `config/events.ts`의 템플릿이다(D18). 참가자 이름을 넣지 않는다.

### D36. 결과 발표는 사람에게 필요한 만큼만 개인 안내로 하고, 하우스 전체에는 커플 목록만 알린다
- 사람에게(`participants:[사람]`): 본인의 최종 선택, 그 상대의 최종 선택, 성사 여부. 하우스 전체에: 시작 안내, 성사된 커플 목록, 종료 멘트(game-rules.md §6.4 공개 범위).
- 짝사랑으로 끝난 다른 참가자들의 선택은 어디에도 공개하지 않는다. 매칭 계산 결과는 `MATCHES_COMPUTED`(server)로 남긴다.
- 에필로그는 사람이 닫을 때까지 기다리고, 닫으면 회차가 `finished`로 끝난다. 일정 중간에 핸들러가 없는 단계를 만나면 지금처럼 `schedule_end`로 끝난다.

## 4. 아키텍처

```
 apps/web (React)
     │  WebSocket: 사람 시점 ViewPatch ↓ / 명령 ↑
     ▼
 apps/server ── 조립(composition root): Fastify + ws, 추론 구성(env), CLI(sim·audit·doctor), 시뮬레이터
     │
     ├── packages/runtime    오케스트레이터: Game, Director·StageRegistry, 단계 핸들러, ChatScene(발언 진행),
     │                       GpuQueue, GameClock(일시정지 인식), HumanViewProjector, HumanGateway, audit
     ├── packages/inference  LlmPort·ImagePort 구현: LlamaCppLlm, FakeLlm, SdCppImage, FakeImage,
     │                       GpuLease 구현(PassthroughLease, ProcessGpuLease), LlamaServerProcess
     ├── packages/store      SQLite 회차 저장소: events, deliveries, llm_calls, 마이그레이션
     ├── packages/config     기본 설정과 캐스팅 풀(데이터만)
     │
     ├── packages/agents     ObservationView(시점 제한), 프롬프트, TaskSpec, AgentRunner, 출력 검증,
     │        │              포트 인터페이스(LlmPort, ImagePort, GpuLease), FakeLlm 응답기
     │        ▼
     └── packages/engine     순수 로직: 상태 fold, 가시성, 투표·매칭, 방 배정, 발언자 점수, 궁합·관계 계산, 캐스팅 구조
              ▼
         packages/shared     zod 스키마: 도메인, 이벤트, 설정 타입, 프로토콜(ViewPatch, Command, applyPatch)
```

### 4.1 의존 방향

```
shared ← engine ← agents ← (inference, store) ← apps/server
                agents ← runtime ← apps/server
shared ← config ← apps/server
shared ← apps/web
```

- `engine`은 I/O를 하지 않는다. 파일, 네트워크, DB, 시계, 난수를 직접 쓰지 않고 주입받는다.
- `agents`는 `LlmPort`·`ImagePort`·`GpuLease` 인터페이스만 알고, 구현체(`inference`)는 모른다. `runtime`도 어댑터를 모른다. 조립은 `apps/server`에서만 한다.
- 단계 핸들러와 엔진은 설정을 인자로 받는다. `config` 패키지를 직접 import하지 않는다.
- 방향은 `dependency-cruiser` 규칙(`.dependency-cruiser.cjs`)으로 품질 게이트에서 강제한다. 선언하지 않은 패키지 import도 오류로 잡는다.
- `apps/web`은 `shared`만 import한다.

### 4.2 확장 지점

모든 확장 지점은 인터페이스와 레지스트리로 만든다. 기능을 추가할 때 오케스트레이터 코드를 고치지 않는 것이 목표다.

| 확장 | 방법 |
|---|---|
| 새 일정 단계·이벤트 | `StageHandler` 구현 + 단계 레지스트리 등록. 상태 머신은 설정(`config/schedule.ts`)의 단계 목록을 따른다 |
| 새 LLM 작업 | `TaskSpec`(출력 스키마, 최대 토큰, 우선순위, 프롬프트 빌더, 검증기 목록) 등록 |
| 새 출력 검증 규칙 | `Validator` 구현 + 작업별 파이프라인에 추가 |
| 새 모델·추론 엔진 | `LlmPort` 구현 |
| 새 저장소 | `EventStore` 인터페이스 구현 |
| 캐스팅 풀·활동 목록·상황 카드 | `config/src/pools.ts`, `config/src/events.ts`. 코드 수정 없음 |
| 매칭 규칙(성별 구성 등) | 선택 가능 여부는 성별이 아니라 `eligibleTargets(run, voter)` 함수로 판정한다. 기본 구현은 이성만 허용한다 |

### 4.3 한 번의 대사 생성 흐름

```
이벤트 발생(예: 사람 메시지) ─▶ engine: 상태 갱신 + 발언 후보 점수 → 발언자 선정
  ─▶ GpuQueue.enqueue(TaskSpec=dialogue, speaker, priority, sceneVersion)
  ─▶ agents.ContextBuilder: ObservationView(speaker)로 컨텍스트 조립 → deliveries 기록
  ─▶ LlmPort.generate(schema) ─▶ 검증 파이프라인
        ├ 통과 + 컨텍스트가 여전히 유효 → MESSAGE_SENT 이벤트 → projection → View 이벤트 전송
        ├ 실패 → 1회 재생성 → 또 실패하면 LLM_OUTPUT_REJECTED 기록 후 건너뜀
        └ 낡음(방 종료, 새 사람 메시지) → 폐기
```

### 5.1 이벤트

```ts
interface GameEvent {
  run_id: RunId
  seq: number                  // 회차 안에서 단조 증가, 유일
  event_id: EventId
  type: EventType              // MESSAGE_SENT, PARTICIPANT_JOINED, VOTE_COMMITTED, ...

  schema_version: number
  idempotency_key?: string     // 중복 명령·이벤트 차단
}

type Visibility =
  | { kind: 'room' }                             // 발생 시점의 방 멤버
  | { kind: 'house' }                            // 발생 시점에 입장해 있던 모든 참가자
  | { kind: 'participants'; ids: ParticipantId[] } // 지정한 참가자만 (투표는 본인만)
  | { kind: 'server' }                           // 서버 내부 전용 (궁합, 숨은 취향, LLM 원문)
```

### 5.2 저장 (D29)

회차 하나가 `runs/<run_id>/run.sqlite` 파일 하나이고, 프로필 사진은 같은 디렉터리의 `avatars/`에 둔다.

| 테이블 | 성격 | 비고 |
|---|---|---|
| `events` | **원천** | `seq` 기본키, `idempotency_key` 유일. 읽을 때 zod로 payload를 다시 검증한다 |
| `deliveries` | 감사 | call_id, owner_id, task, attempt, seq_at_call, 근거 event seq 목록, memory id 목록, 프롬프트 원문 |
| `llm_calls` | 운영 | call_id, task, owner, attempt, 처리 시간, 토큰 수, 결과(accepted/rejected/error/aborted), 거부 사유 |
| `meta`, `schema_version` | 메타 | run_id, 순차 마이그레이션 |

- 나머지 상태(참가자, 방·멤버십, 투표, 관계, 말투, 기억, 상호작용 가중치)는 `RunState`가 이벤트를 접어서 만든다.
- 멤버십은 시각이 아니라 이벤트 `seq` 구간으로 저장한다. 같은 시각에 이벤트가 여러 개 있어도 판정이 모호해지지 않는다.
- 회차끼리 데이터를 공유하지 않는다. 파일이 다르기 때문이다(원칙 6).

## 6. 정보 격리

### 6.1 가시성 판정

`engine/visibility.ts`의 `canObserve(run, participantId, event)` 하나가 모든 판정을 맡는다.

| visibility | 관찰 가능 조건 |
|---|---|
| `room` | 이벤트 `seq` 시점에 그 방의 멤버였다 (`joined_seq ≤ seq < left_seq`) |
| `house` | 이벤트 시점에 하우스에 입장해 있었다 |
| `participants` | 목록에 있다 |
| `server` | 아무도 볼 수 없다 |

나중에 방에 들어와도 그 전의 대화는 보이지 않는다. 늦게 입장한 참가자는 입장 전의 자기소개를 알지 못한다.

### 6.2 접근 경로를 하나로 제한한다

- `agents` 패키지가 이벤트에 접근하는 유일한 API는 `ObservationView(owner)`다. 원본 이벤트를 조회하는 함수는 `agents`에 노출하지 않는다(패키지 export와 dependency-cruiser로 강제).
- 기억 요약의 입력은 소유자가 관찰한 이벤트와 소유자의 기존 기억뿐이다. 요약 결과의 `source_event_ids`는 입력에 들어간 ID의 부분집합이어야 하고, 아니면 거부한다.
- PD 컨텍스트에는 공개 일정과 그 순간 발표할 확정 결과만 넣는다. MVP에서 PD는 템플릿이므로 해당하지 않는다(D18).
- 사람 시점의 View도 같은 `canObserve`로 만든다. 사람도 참가자이기 때문이다.

### 6.3 프로필 공개

참가자가 다른 참가자에 대해 아는 신상은 `PROFILE_DISCLOSED` 이벤트로만 늘어난다.

- 이름: 입장할 때 `house` 공개. 동시에 이미 와 있던 사람들의 이름을 새 입주자에게만(`participants`) 공개한다(D30).
- 나이와 직업: 1일차 저녁 자기소개 때 공개
- 자기소개 시점에 하우스에 있던 참가자만 알게 된다. 메기는 입장할 때 자기 정보를 공개하지만, 기존 참가자의 나이·직업은 대화로 들어야 안다.

프로필 화면과 AI 컨텍스트 모두 이 공개 상태를 따른다.

### 6.4 감사(audit)

`pnpm audit:run <run_id>`가 다음을 확인한다.

1. `deliveries`의 모든 event_id에 대해, 호출 시점에 `canObserve(owner, event)`가 참이었다.
2. 모든 memory_id의 소유자가 그 호출의 owner다.
3. canary 값이 허용되지 않은 시점의 컨텍스트나 출력에 나타나지 않았다. 대상은 입장 전 메기의 이름, 타인의 투표 대상 ID, server 가시성 payload의 고유 문자열이다.
4. 모든 `memories.source_event_ids`가 소유자에게 관찰 가능한 이벤트였다.

시뮬레이션 테스트(§15)는 매 판 끝에 audit를 돌리고, 위반이 0건이어야 통과한다.

## 7. LLM 하네스

### 7.1 LlmPort

```ts
interface LlmPort {
  generate<T>(req: {
    task: TaskId
    messages: ChatMessage[]
    schema: JsonSchema          // llama-server response_format(json_schema)로 출력 제약
    maxTokens: number
    sampling: Sampling
    signal: AbortSignal         // 낡은 요청 취소
  }): Promise<LlmResult<T>>

```

구현체는 세 가지다.
- `LlamaCppLlm`: `POST /v1/chat/completions`, `chat_template_kwargs.enable_thinking=false`
- `FakeLlm`: 시드 기반 규칙 응답, 지연 시뮬레이션
- `ReplayLlm`: 이벤트 로그에 저장된 출력을 그대로 돌려준다

### 7.2 작업(TaskSpec)

| 작업 | 출력 | 최대 토큰(초기) | 우선순위 |
|---|---|---|---|
| `dialogue` (단체방) | `{action: speak\|silent, text}` | 120 | P0(사람에게 답할 때) / P1 / P4 |
| `private_dialogue` (1:1) | 위와 같음 | 160 | P0 / P4(백그라운드) |
| `greeting` (입장 인사) | 위와 같음 | 80 | P1 |
| `self_intro` | `{text}` (나이·직업은 서버가 끼워 넣음) | 120 | P1 |
| `invite_decision` | `{accept: id[]}` (enum) | 60 | P2 |
| `vote` | `{target: id\|"none", reason}` (enum) | 120 | P2 |
| `activity_choice` | `{first, second}` (enum) | 40 | P2 |
| `signal_card` | `{target: id\|"none", text}` | 100 | P2 |
| `mailbox_question` / `mailbox_answer` | `{target, text}` / `{text}` | 100 | P2 |

최대 토큰은 Phase 1에서 한국어 토큰화 실측 후 조정한다.

### 7.3 생성 파라미터

- 초기값: `temperature 0.7, top_p 0.8, top_k 20, min_p 0`. 참가자마다 temperature에 ±0.1 오프셋을 준다.
- `presence_penalty`는 Phase 1에서 0과 1.0~1.5를 비교해 정한다.
- 판단 작업(vote, invite, activity, relationship_eval)은 `temperature 0.5`로 시작한다.

### 7.4 프롬프트 구성

순서를 고정한다. 바뀌지 않는 부분을 앞에 두어 접두사 캐시를 쓸 수 있으면 쓴다.

```
[ROLE + 공통 규칙]       고정 문구 (작업별)
[인물]                   자연어 프로필 + 말투 규칙 + 예시 대사 3~5줄
[현재 상황]              날짜·시각, 장소, 진행 중 이벤트, 같은 방에 있는 사람(이름만)
[알고 있는 사실]         known_facts (본인이 아는 것만)
[관계]                   같은 방 사람들에 대한 인상 요약 + 말투(존댓말/반말) + 궁합 힌트
[관련 기억]              요약·인상 (§9.3)
[최근 대화]              이 방에서 본인이 관찰한 최근 메시지. "이름: 내용" 형식
[지금 할 일]             작업 지시 한두 줄
[출력 규칙]              형식, 길이, 금지 행동
```

- 다른 참가자의 발언은 프롬프트 안에서 인용 데이터로 감싼다. 사용자가 "PD 공지: …"라고 써도 지시로 해석되지 않게 한다.
- 공통 규칙은 기획서 §11.1의 내용을 짧게 줄여 쓴다. 비공개 정보 모름, 제공된 것만 사실, 모두에게 친절할 의무 없음, 다른 사람 대사 금지, 일정·투표 선언 금지, 침묵 가능.
- "사용자를 우대하지 마라"는 넣지 않는다. 사용자를 표시하지 않는 것(D19)으로 해결한다.

### 7.5 출력 검증 파이프라인

순서대로 적용하고, 하나라도 실패하면 거부한다.

1. 스키마. JSON Schema로 제약하지만 다시 검증한다.
2. 길이. 작업별 글자 수 상한이다(단체방 기본 80자, 1:1 120자). 넘으면 문장 단위로 자르고, 자를 수 없으면 거부한다.
3. 대리 발언. `^\s*[가-힣A-Za-z]{1,8}\s*[:：]` 형태로 시작하는 줄이 있거나, 다른 참가자 이름 뒤에 콜론이 붙어 있다.
4. 사칭. `PD`, `제작진`, `[공지]`, `[시스템]`처럼 설정에 둔 패턴이다.
5. canary. 화자가 아직 모르는 참가자의 이름(alias 포함)이 나온다.
6. 반복. 화자 본인의 최근 발언 5개와 비교한다. 문자 3-gram Jaccard 유사도가 임계값을 넘거나, 두 문장 모두 3-gram이 8개 이상이면서 겹침 계수(교집합 / 작은 쪽 크기)가 0.8 이상이면 거부한다. 겹침 계수는 "안녕하세요, 서윤이에요." 다음에 "안녕하세요, 서윤이에요. 다들 반가워요."처럼 앞말을 통째로 되풀이하고 덧붙이는 경우를 잡는다. 이런 경우는 길이가 달라서 Jaccard만으로는 놓친다.
7. 유효성. 방이 닫혔거나 컨텍스트가 낡았다(§7.7).

되풀이 문장도 검증 전에 지운다. 3일 완주 대화록에서 참가자들이 다른 사람의 문장을 이모티콘까지 그대로 옮기거나("저도요! 제가 주말에 러닝도 해요. 😄"), 같은 문장을 메시지마다 끝에 붙였다. 메시지 전체 유사도(6번 반복 검사)로는 둘 다 잡히지 않는다. 그래서 그 방의 최근 메시지 10개(누가 했든)를 문장으로 나눠, 새 대사의 문장 중 3-gram 유사도나 겹침 계수가 높은 문장을 지운다(`dropEchoedSentences`). 다 지워지면 반복으로 거부하고 다시 만든다. 8글자 미만의 짧은 반응("저도요!")은 남긴다.

호칭도 검증 전에 후처리한다. 4B 모델은 영어처럼 "수아, 주말엔 ~", "안녕하세요, 우진!"처럼 이름만 불러 말을 건다(실측). 메시지 맨 앞의 호칭은 지우고, 존댓말 사이에서 문장 중간에 이름만 부르면 "씨"를 붙인다(`fixAddress`). 존댓말 검증(D13)은 어미만 보지 않는다. "안녕,", "야,", "나/내", "수아야" 같은 반말 낱말과 호칭도 거부하고, 마지막이 아닌 문장도 분명한 반말 어미("~거든", "~네", "~구나")면 거부한다. "맛있겠다!" 같은 혼잣말 감탄은 존댓말 사이에서도 흔하므로 마지막이 아닌 문장의 "-다"는 허용한다. 한국어 대사 속 소문자 영단어("people")는 외국 문자 누출로 본다. 대문자로 시작하는 이름·약어와 아는 참가자 이름은 허용한다.

웃음 표현은 검증과 별도로 후처리한다. 말투 파라미터 `laughter`가 `LAUGH_THRESHOLD`(0.65) 미만인 인물은 대사와 예시 대사에서 ㅋ·ㅎ를 지운다. 기준 이상인 인물도 한 메시지에 한 번, 두 글자까지만 남긴다. 4B 모델은 프롬프트로 "웃음 표현을 쓰지 않는다"고 해도 잘 지키지 않아서 코드로 강제한다. 지운 결과가 빈 문자열이면 침묵으로 처리한다.

거부하면 1회 재생성하고, 또 실패하면 건너뛴다. 건너뛴 기록은 `LLM_OUTPUT_REJECTED` 이벤트(server 가시성)로 남긴다. 패턴과 임계값은 `config/validation.ts`에 둔다.

### 7.6 GpuQueue

| 우선순위 | 요청 |
|---|---|
| P0 | 사람이 기다리는 직접 응답 |
| P1 | 장면 진행에 필요한 응답(입장 인사, 자기소개) |
| P2 | 투표·초대·선택 판단 |
| P3 | (예약) LLM PD 멘트 |
| P4 | 백그라운드 장면 대사 |
| P5 | 기억 요약, 관계 평가 |

- 마감이 있는 요청은 남은 시간이 예상 처리 시간의 2배 아래로 떨어지면 P2로 승격한다.
- 한 참가자당 동시에 진행 중인 요청은 하나다.
- 요청에는 `sceneVersion`을 붙인다. 이미 낡은 요청은 꺼낼 때 버리고, 처리 중이면 `AbortSignal`로 취소한다.
- 실패하면 1회 재시도한다. llama-server에 연결할 수 없으면 큐를 보존하고 게임을 일시정지한다(`LLM_UNAVAILABLE`).

### 7.7 낡은 응답 처리

- 각 방에는 `version`이 있다. 사람 메시지가 들어오거나 방이 닫히면 증가한다.
- 응답이 도착했을 때 방이 닫혔으면 폐기한다.
- 생성 시작 이후 그 방에 사람 메시지가 새로 들어왔다면 처리는 이렇다. 사람 메시지에 답하던 P0 응답은 내보낸다. 사람 메시지를 보지 못한 AI 연쇄 대사(P1/P4)는 폐기하고 스케줄러가 다시 고른다.

## 8. 인격 생성

### 8.1 파이프라인

온보딩에서 사용자가 성별과 나이를 입력하면 바로 시작한다. 나머지 항목을 입력하는 동안 백그라운드에서 진행된다.

1. **구조 제약(서버, 시드)**
   - 성별 구성: 이성 AI 3명, 동성 AI 2명, 메기 남녀 각 1명.
   - 나이: 사용자 나이 ±3세, 만 19세 이상, 같은 나이는 최대 2명.
   - 직업: `config/pools/occupations.ts`에 최소 나이가 있는 범주에서 뽑는다.
   - 그 밖에 지역과 입장 순서를 정한다.
2. **성향 벡터 다양성 샘플링.** 외향성, 개방성, 적극성, 감정 표현, 유머의 후보를 많이 뽑는다. 그다음 최원점 샘플링(farthest-point sampling)으로 서로 먼 7개를 고른다.
3. **숨은 취향.** 성향 축에 대한 선호 벡터를 만들고, 싫어하는 성향 1~2개를 정한다(server 가시성).
4. **말투 파라미터.** 평균 길이, 웃음 표현 빈도, 이모티콘 빈도, 질문 경향, 유머 스타일, 기본 존댓말 정도를 정한다.
5. **이름.** 성별 풀에서 뽑는다. 성+이름 전체와 이름 2글자가 모두 겹치지 않게 하고, 어떤 전체 이름도 다른 사람(사용자 포함)의 부르는 이름을 품지 않게 한다(D31).
6. **LLM 생성.** 참가자마다 작은 JSON을 3번 만든다.
   - (a) 배경, 가치관, 취향 세부, 장단점, 갈등 대응
   - (b) 말투 자연어 묘사 + 예시 대사 5줄(맞장구, 공감하며 덧붙이기, 놀람, 가벼운 농담, 쑥스럽거나 곤란할 때). 인사·자기소개·질문은 넣지 않는다. 4B 모델은 예시 대사의 내용까지 그대로 옮겨 써서, 인사 예시는 어색한 입장 인사가 되고 "쉬는 날 뭐 해요?" 예시는 흐름과 상관없는 주말 질문이 됐다(실측). 프롬프트에서도 예시는 "어투만 참고한다"고 표시한다.
   - (c) 공개해도 되는 정보와 아직 말하지 않은 정보
7. **정합성·다양성 검사.**
   - 나이와 직업·경력이 맞는가.
   - 구조 제약과 생성 결과가 일치하는가. 지역과 취미가 바뀌지 않았는가.
   - 직업이 3명 이상 겹치지 않는가.
   - 취미 Jaccard 유사도가 임계값 아래인가.
   - 예시 대사의 참가자 간 문자 3-gram 유사도가 임계값 아래인가.
   - 단점과 싫어하는 성향이 비어 있지 않은가. 모두가 지나치게 긍정적으로 설정되지 않았는지 확인하는 항목이다.
   실패한 부분만 다시 생성하고(최대 2회), 그래도 실패하면 템플릿 문장으로 대체한다.

예상 비용은 7명 × 3회 × 약 5초로 2분 안팎이다. 그동안 PD 캐스팅 화면을 보여 준다. 실제 시간은 Phase 1 실측으로 갱신한다.

### 8.2 저장

- 구조화 필드와 자연어 프로필을 둘 다 저장한다. 게임 중에는 바꾸지 않는다.
- 메기는 온보딩 때 생성하지만 입장 전에는 어떤 장면에도 참여하지 않는다. 메기의 이름은 canary다.

### 8.3 프로필 사진 (D22, D27)

1. **외모 속성(서버, 시드).** `config/pools/appearance.ts`에서 뽑는다. 머리 모양과 색, 옷차림, 분위기, 배경, 표정, 조명이다. 같은 회차 안에서 머리 모양과 옷차림이 겹치지 않게 한다. 같은 속성을 인격 생성 LLM 입력에도 넣어서, 글로 된 설정과 사진이 어긋나지 않게 한다.
2. **프롬프트 조립.** LLM을 쓰지 않고 영어 템플릿으로 조립한다. 번역 오류와 지시 무시를 피하기 위해서다. 예: `portrait photo of a fictional {age}-year-old Korean {woman|man}, {hair}, wearing {outfit}, {expression}, {background}, soft natural light, 85mm, shallow depth of field`. 항상 성인 나이를 넣고, 실존 인물 이름은 넣지 않는다.
3. **생성.** 인격 텍스트 생성이 끝나면 다음 순서로 진행한다.
   - `GpuLease.acquire('image')`: llama-server를 내리고 stable-diffusion.cpp를 올린다.
   - 7장을 순서대로 만든다. 768×768, 4스텝, 시드는 `hash(run_seed, participant_id)`라 재현할 수 있다.
   - `GpuLease.acquire('llm')`로 원상 복구한다.
   - 장당 타임아웃이 있다. 실패한 사람만 기본 아바타를 쓴다.
4. **저장.** `runs/<run_id>/avatars/<participant_id>.png`. 회차 기록을 지우면 함께 지운다.
5. **표시.** 프로필과 채팅 목록에서 쓴다. UI에는 "AI로 생성한 가상 인물"을 표시한다. 사람 참가자는 사진 없이 이니셜 아바타를 쓴다.
6. **인터페이스.** `ImagePort.generate({prompt, seed, width, height, steps}) → png`. 구현체는 `SdCppImage`(stable-diffusion.cpp)와 `FakeImage`(시드 기반 그라디언트 PNG)다. stable-diffusion.cpp를 상주 서버 모드로 쓸지 장마다 CLI를 띄울지는 Phase 1에서 확인한다. 모델을 한 번만 올리는 서버 모드를 우선한다.

예상 추가 시간은 프로세스 교대 2회(약 20초)와 7장 × 약 5초로 1분 안팎이다. Phase 1에서 실측한다.

## 10. 관계 엔진과 선택

### 10.1 상태

방향이 있는 쌍(A→B)마다 `interest, comfort, trust, curiosity, confidence`를 0~100으로 둔다. 초기값은 설정으로 정한다. `compatibility`는 저장하지 않고 §10.2로 계산한다.

### 10.2 궁합과 노출량

```
compat_true(A→B)  = similarity(prefs_A, traits_B) − dealbreaker 페널티        // 캐스팅 때 고정, server 전용
exposure(A,B)     = 1 − exp(−w(A,B) / k)
w(A,B)            = Σ 상호작용 가중치
                    (1:1 발언 1.0, 서로를 향한 단체방 발언 0.5,
                     백그라운드 장면 발언 2.0 ← 압축 보정, D21)
compat_eff(A→B)   = 50 + (compat_true − 50) × exposure
```

`compat_eff`는 숫자로 프롬프트에 넣지 않는다. 구간별 자연어 힌트로 바꿔 관계 섹션에 넣는다. 예: "이야기할수록 결이 잘 맞는다고 느낀다", "아직 잘 모르겠다", "어딘가 템포가 다르다고 느낀다". 대화를 많이 할수록 진짜 궁합이 드러나는 구조다. 상수 `k`와 가중치는 `config/relationship.ts`에서 조정한다.

### 10.3 갱신

- 의미 있는 장면(1:1, 그룹 활동, 카드·우체통, 하루 종료)이 끝나면 `relationship_eval`을 부른다.
- 축별 `-2..+2`를 받아 1단위를 4점으로 환산하고, 한 번에 축당 ±8점으로 제한한다.
- LLM이 `significant: true`와 근거를 함께 주고, 그 장면이 1:1이나 카드·우체통일 때만 상한을 ±16으로 늘린다.
- `evidence_event_ids`는 그 호출에 제공된 이벤트의 부분집합이어야 한다.
- 금지 사항(기획서 §34.4)은 코드 경로가 아예 없게 만든다. 사용자 보정, 인기 조정, 메기 등장 시 일괄 감소, 매칭률 맞추기가 그 대상이다.

### 10.4 투표 판단

- 후보는 `eligibleTargets`로 정하고 순서를 섞는다.
- 후보마다 본인의 관계 요약(자연어), 궁합 힌트, 핵심 기억 1~2개를 넣는다. 이전 투표 단계에서 본인이 한 선택도 넣는다.
- 출력은 `{target, reason}`이다. `reason`은 본인의 `choice` 기억으로 저장한다.
- 서버는 결과를 바꾸지 않는다. 2회 실패하면 유보로 확정하고 오류를 기록한다. 인기 참가자를 대신 고르지 않는다.

## 11. 발언 스케줄러

누가 말할지는 스케줄러가 정하고, 무엇을 말할지는 그 참가자의 LLM 호출이 정한다.

### 11.1 점수

새 메시지가 오면 같은 방의 AI마다 점수를 매긴다.

```
score = 지목됨(+큰 값) + 관심 주제 일치 + 직전 대화 참여 + 성향 기본값(외향성)
      + 화자에 대한 interest − 최근 발언 횟수 페널티 − 연속 발언 페널티
```

점수를 softmax로 바꾸고 주입된 `Rng`로 샘플링한다. 가중치는 `config/scheduler.ts`에 둔다.

- **지목 감지.** 참가자마다 alias 목록을 둔다. 전체 이름, 이름 2글자, 이름+씨/님/아/야/이(받침 규칙)를 정규식으로 찾는다.
- **관심 주제.** 메시지를 참가자의 관심사 키워드와 비교하는 단순 매칭으로 시작한다.

### 11.2 규칙

- 사람 메시지 하나에 1~2명이 응답한다. 지목된 사람이 있으면 그 사람이 우선이다.
- 사람 메시지 이후 AI 연쇄 발언은 최대 3개까지 하고, 그다음에는 사람 입력을 기다린다.
- 한 AI는 연속으로 최대 2번까지 말한다.
- 방이 조용하면(20~40초, 무작위) 외향성에 비례한 확률로 한 명이 새 화제를 꺼낸다.
- 오랫동안 말하지 않은 참가자에게는 기회를 준다. 기본은 8분 동안 0회일 때다. 그래도 LLM이 `silent`를 고를 수 있다.
- 메시지 간격은 최소 1.2초다. 타이핑 지연은 `1.0s + 0.05s × 글자 수`(최대 4초)에서 이미 쓴 생성 시간을 빼서 계산한다.

### 11.3 백그라운드 장면

사람이 없는 방의 장면이다. 같은 스케줄러를 사람 없이 돌리고, 목표 발언 수(기본 4~6개)에 도달하거나 장면 시간이 끝나면 종료한다. 생성하지 못한 장면은 기록하지 않는다. "A와 B가 친해졌다" 같은 결론만 저장하지 않는다.

## 12. 시간과 타이머

- **두 시계.** 단조 경과 시간(`wall_elapsed_ms`)과 프로그램 속 시각(`sim_time`)을 따로 둔다. 단계마다 `sim_time` 시작값이 정해져 있다(예: 1일차 심야 23:00).
- **타이머.** 장면 단위로 둔다. 일시정지하거나 저장할 때 `remaining_ms`를 기록한다.
- **사람이 참여한 1:1의 유효 시간.** 사람이 AI 응답을 2초 넘게 기다리는 동안에는 타이머가 멈춘다. 모델 지연 때문에 대화 시간이 줄지 않게 하기 위해서다.
- **종료 처리.** 종료 15초 전에 PD 안내를 보낸다. 종료 시각 전에 생성을 시작한 AI 응답은 10초의 유예 안에 도착하면 내보낸다. 그 뒤 방은 읽기 전용이 된다.
- **자리 비움.** 단체방에서는 사람이 없어도 AI가 짧게 대화를 이어 간다. 사람의 필수 1:1에서는 60초 동안 입력이 없으면 타이머를 멈추고 "계속하기"를 띄운다.
- **연결 끊김.** 게임을 일시정지한다. 재접속하면 마지막 `seq` 이후의 View 이벤트를 다시 보내고 남은 시간을 복원한다.

- 한국어 글자당 토큰 비율.
- 하이브리드 구조에서 llama.cpp 접두사 캐시 재사용이 되는지. 순환 상태 때문에 제한될 수 있다.
- JSON Schema 제약을 켰을 때 속도와 한국어 품질.
- 성능 기준(SLO)은 최소 사양에서 잰 값으로 판정한다.

목표 SLO(Phase 1에서 확정): 최소 사양 기준 P0 응답 p95 5초 이하.

## 14. 프론트엔드

- **화면.** 온보딩(PD 캐스팅), 메인 채팅(현재 방, 일정, 남은 시간, PD 공지), 참가자 프로필(공개된 정보만), 1:1 화면, 투표·선택 화면(최종 선택은 확인을 두 번), 초대 수락, 활동 선택, 시그널 카드, 우체통, 결과 발표, 에필로그.
- **프로토콜.** `shared/protocol.ts`의 zod 스키마를 쓴다.
  - 서버→클라이언트: `ViewEvent`. 이미 사람 시점으로 걸러진 것만 보낸다(D23). 타이핑 표시 신호도 여기에 포함된다.
  - 클라이언트→서버: 명령. `sendMessage`, `vote`, `respondInvite`, `skipTalk`, `chooseActivity`, `sendCard`, `askQuestion`, `answerQuestion`, `continue` 등. 모든 명령에 `command_id`를 붙여 중복 처리를 막는다.
  - 재접속하면 클라이언트가 마지막 `seq`를 보내고, 서버가 그 뒤의 이벤트를 다시 보낸다.
- **AI 안내.** 게임 시작 시 모든 참가자가 AI로 생성된 가상 인물임을 안내한다.
- **관전 뷰.** `--dev-observer`로 켜는 개발용 화면이다. 참가자별 시점, deliveries, 관계 수치, GpuQueue 상태를 보여 준다. Phase 2부터 쓴다.
- 상태 관리 라이브러리는 Phase 3에서 화면이 늘어날 때 정한다. 그 전에는 `useReducer` + 컨텍스트로 충분하다.

## 15. 검증 체계

### 15.1 품질 게이트

`pnpm check` 한 번으로 돌린다. 커밋 전에 통과해야 한다.
- `tsc --noEmit`(strict), `eslint`, `dependency-cruiser`(§4.1)
- `vitest` + 커버리지. `engine` 커버리지 하한은 90%다.

### 15.2 테스트 층

| 층 | 대상 | 도구 |
|---|---|---|
| 단위 | 상태 머신 전이, 투표 검증, 매칭, 방 배정, 가시성, 검증기, alias 매칭, 궁합 계산 | vitest |
| 속성 기반 | 불변식: 관찰 불가능한 이벤트가 컨텍스트에 없다, 한 참가자는 같은 시간에 한 방에만 있다, 매칭은 대칭이다, 필수 대화는 모두 배정된다, 재생 결과가 같다 | fast-check |
| 시나리오 | 기획서 §46.5의 투표 상황 9종, §46.6의 타이머 상황 | vitest + FakeClock |
| 시뮬레이션 | FakeLlm으로 3일 전체를 시드 1,000개로 자동 진행하고 매 판 audit 위반 0건 | `pnpm sim --seeds 1000` |
| 계약 | 실제 llama-server: 스키마 준수율, thinking off 동작, 취소 동작 | `pnpm test:llm` (수동, 로컬) |

단위·속성·시나리오·시뮬레이션 테스트는 네트워크를 쓰지 않는다.

### 15.3 품질 측정 (실제 모델)

`pnpm eval:dialogue`는 고정 장면 세트(거실 3명, 1:1, 입장)를 실제 모델로 돌리고 지표를 낸다.
- 화자 간 말투 구별도: 같은 질문에 대한 답의 화자 간 문자 n-gram 유사도, 어미 분포 차이
- 질문으로 끝나는 비율
- 발언 길이 분포
- JSON 실패율, 검증 거부율과 그 사유
- 대리 발언과 canary 발생 건수

### 15.4 사람 평가

기획서 §46.8의 8개 기준을 5점 척도로 매긴다. Phase 2 종료 시 "참가자 성격이 구별되는가"와 "한국어 구어체가 자연스러운가"가 기준에 못 미치면 D4 재검토 조건에 해당한다.

## 16. 운영성

- **구조화 로그.** JSON 한 줄 형식으로 `runs/logs/`에 남긴다. 상관 키는 `run_id`, `call_id`, `seq`다.
- **`pnpm doctor`.** Node 버전, llama-server 연결, 모델 파일, 채팅 템플릿 인식, thinking off 응답, VRAM, DB 쓰기 권한을 진단하고 해결 방법을 출력한다.
- **`pnpm bench`.** 고정 프롬프트 세트로 지연과 tok/s를 잰다. 결과는 `docs/perf/`에 날짜별로 남긴다.
- **회차 기록.** `runs/<run_id>/run.sqlite`에 저장한다(사진은 `runs/<run_id>/avatars/`). 게임이 끝나면 사용자가 보관하거나 삭제할 수 있다. 새 게임은 이전 파일을 열지 않는다.
- **로컬 전용.** llama-server와 게임 서버 모두 `127.0.0.1`에만 바인딩한다. 원격 텔레메트리는 없다.
